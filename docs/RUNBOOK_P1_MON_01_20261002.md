# P1-MON-01 운영 Runbook — 구축·확인·장애 복구·Rollback·Known Limitation (2026-10-02)

책임: [#17](https://github.com/321Team/fds-project-baseline/issues/17) MON Lead 이재환, Support 이권욱, 보안 검토 이하영. 이 문서는 #17 Runtime AC "Resource/PVC/Retention/Single-Replica Known Limitation과 구축·복구·Rollback 절차가 Runbook에 기록된다"와 본문 "Rollback / Recovery"(Component 중지·복구 → PVC 확인 → Target 재등록 → Alert Silence/복구 → Watchdog 정상화)의 기록이다.

- 각 절차 옆의 **[검증]**은 표시한 증적에서 실제로 실행해 확인한 것이고, **[NOT RUN]**은 절차만 적고 아직 실행하지 않은 것이다.
- 이 문서는 실행 지시나 승인 기록이 아니다. 실행 여부와 시점은 MON Lead가 정하고, 클러스터 변경은 기존 변경 창·Gate를 따른다.

## 0. 공통 전제

- 클러스터 명령은 기존 승인 kubectl 경로(control01 `server02`)에서 실행한다. 아래 예시의 `K`는 `sudo kubectl --kubeconfig=/etc/kubernetes/admin.conf -n monitoring-api`다. 새 계정·권한·Secret을 만들지 않는다.
- monitor01 명령은 `server01_monitor`(rootless podman)로 실행한다. 루트 권한이 필요한 단계만 `sudo`를 쓴다.
- 서버에서 쓰는 셸 명령에는 `set -e`와 `!`를 쓰지 않는다. 결과는 작업 폴더(`~/p1-mon-<작업>-<시각>/`)에 파일로 남기고 `sha256sum`을 함께 기록한다.
- Secret 값·webhook URL·Basic Auth 암호·개인키는 출력·기록·Git에 남기지 않는다(`kubectl get secret -o yaml` 금지).
- 전체 디렉터리를 `kubectl apply -f kubernetes/monitoring/`로 한 번에 적용하지 않는다. 객체 단위로 `kubectl diff` → 백업 → `apply` → 사후 `diff` 0 순서를 지킨다.
- 병합은 현장 반영 승인이 아니다. 이미지는 #13 HBR 처분과 #17 QA Gate가 열린 것만 반영한다.

## 2. 구축

### 2.1 클러스터 [검증: 9/22 최초 배포, 9/30~10/2 교체 — evidence#84·#89·#93]

1. 전제: `fds-app` 앱 Pod, Harbor pull Secret `harbor-pull-secret`, Grafana admin Secret `grafana-admin-credentials`(직접 생성, 값 비기록)가 있어야 한다.
2. 적용 순서: `namespaces.yaml` → `rbac-kube-state-metrics.yaml`·`prometheus-rbac.yaml`·`monitoring-api-serviceaccounts.yaml` → `pv-monitoring-storage.yaml` → NetworkPolicy(`networkpolicy.yaml`, `monitoring-api-dns-allow.yaml`, `allow-*.yaml`, `alertmanager-egress.yaml`) → ConfigMap·Deployment·DaemonSet(`prometheus.yaml`, `alert-rules.yaml`, `alertmanager-*.yaml`, `grafana*.yaml`, `kube-state-metrics.yaml`, `node-exporter.yaml`, `monitor01-remote-write.yaml`).
3. 이미지 Gate: Harbor digest + Trivy 결과 + #13 HBR 처분(0/0 또는 기록된 예외)이 있어야 `image:`를 바꾼다. 현장 imageID와 Harbor digest를 대조한다.
4. 객체마다: `kubectl diff` 기대 차이 확인 → 현재 YAML 백업(`get -o yaml > pre-<이름>.yaml`) → `apply` → `rollout status` → 사후 확인(1.1 표 값, imageID, Target, health) → 사후 `kubectl diff` rc 0.

### 2.2 monitor01 [검증: 10/1 Gate F·기동, 10/2 자동 기동 — evidence#91·#94]

1. **이미지 반입(Gate F A안):** Harbor → tar → ansible01 → monitor01 `podman load`. 직접 pull과 `--tls-verify=false`는 쓰지 않는다. 대조 사슬은 Harbor manifest → `config.digest` → archive config → 로컬 이미지 ID다(`runtime_launch_local.py verify-image`). 로컬 RepoDigest는 기록만 한다.
2. **호스트 준비(sudo):** 설정·data 경로 생성. 키 접근은 SEC 승인 조건대로 한다: `container_read_certs` on, 상위 폴더 ACL `u:server01_monitor:x`, 키 ACL `u:589819:r`(컨테이너 uid 65532). 키 위치·라벨·소유자는 바꾸지 않는다. htpasswd는 `1000:589819 640`(`podman unshare chgrp 65532`)이고 값은 기록하지 않는다.
3. **기동:** `runtime_launch_local.py start …`(receiver·blackbox) → `check-nginx` → firewalld rich rule(`.108/32 → .30/32` 443→8443, runtime·permanent) → `start-nginx`.
4. **자동 기동:** `monitor01/systemd/README.md`대로 실행기 폴더·`current` 링크, `images.env`(0600), 유닛 설치 → `sudo loginctl enable-linger server01_monitor` → `systemctl --user enable`. 확인은 재부팅 시험(로그인 전 기동, 유닛 `active/exited`, 컨테이너 3개, listener 3개, heartbeat 수신)으로 한다.
5. **sender:** `monitor01-remote-write.yaml`(Root CA ConfigMap, remote write NP)과 Prometheus remote_write 설정. Basic Auth Secret `monitor01-remote-write-auth`는 값을 기록하지 않고 resourceVersion만 남긴다.

### 4.2 PVC 확인 [NOT RUN: 장애 상황 미발생, 정상 상태 조회는 9/29 기록]

1. `K get pvc` — 3개 `Bound`, `K get pv` — `Retain`, nodeAffinity `k8s-worker03`.
2. Pod가 Pending이면 `K describe pod`로 볼륨 바인딩·노드 상태를 본다. local PV라 worker03이 내려가면 세 Pod는 다른 노드로 옮겨갈 수 없다(6절).
3. 데이터 유지 확인: Prometheus 재시작 뒤 과거 시계열 조회 [검증: #17 AC "Prometheus Pod 재시작 후 PVC 데이터와 Dashboard Query 유지"].
4. PVC를 지웠어도 PV는 `Retain`이다. PV의 `claimRef`를 정리하고 같은 이름의 PVC를 다시 만들면 붙는다. 데이터 경로는 지우지 않는다.

### 4.3 Target 재등록 [검증: 9/30 node-exporter collector 변경 후 reload, 10/2 23/23 확인]

1. ConfigMap을 바꿨으면 `kubectl apply` 뒤 Prometheus에 `POST /-/reload`를 보낸다(재시작 불필요).
2. `/api/v1/targets`에서 DOWN Target의 `lastError`를 본다. 앱 Target은 `fds-app` NetworkPolicy(9091/9090), node-exporter는 Calico HostEndpoint/GNP(9100), kubelet은 10250을 확인한다.
3. `count(up)`과 `count(up==1)`이 다시 23/23이 될 때까지 확인한다.

### 4.4 Alert Silence·복구 [NOT RUN: 절차만]

1. 예정된 작업으로 알림이 예상되면 시작 전에 silence를 만든다: `K exec deploy/alertmanager -- amtool silence add alertname=<이름> --duration=<시간> --comment="<작업·티켓>" --alertmanager.url=http://127.0.0.1:9093`.
2. 작업이 끝나면 `amtool silence query`로 ID를 확인하고 `amtool silence expire <ID>`로 해제한다.
3. 해제 뒤 Alert이 resolved로 바뀌는지 확인한다. 시험 Alert 흐름(Firing → Alertmanager 수신 → Resolved)은 #17 AC로 검증됐다.
4. 외부 알림(Discord)은 `severity=critical`과 `FDSDetectionBurst`만 보내고 나머지는 화면 표시(`screen-only`)다(`alertmanager-config.yaml`, #75 결정). webhook URL은 Secret 파일로만 참조한다.

### 4.5 Watchdog 정상화

1. **heartbeat 단절 firing:** 클러스터 Prometheus 상태 → remote write 실패 지표 → monitor01 nginx 로그(`podman logs fds-monitor01-nginx`, `.108 POST 204` 여부) 순서로 원인을 좁힌다. 클러스터 쪽이 복구되면 해소된다 [검증: firing 09:48:12.9 → 해소 09:50:28, evidence#91].
2. **monitor01 자체 중단:** 4.1 monitor01 행대로 유닛을 재시작하거나 재부팅한다. 재기동 뒤 heartbeat 지연 15초 안팎·Watchdog 없음을 확인한다 [검증: evidence#94].
3. **API LB Probe 실패:** `probe_success` 0이면 API LB `10.1.93.109:6443` 상태를 먼저 본다. 시험용 장애 주입은 `runtime_fault_api_lb.py --ack-hostwide --duration <30~180>`만 쓴다. 이 도구는 자동 회수 timer를 먼저 건다 [검증: 10/2 10:10~10:13, evidence#91].
4. receiver에는 Alertmanager가 없다. Watchdog 상태는 receiver `/api/v1/alerts`로만 확인한다(6절).

## 6. Known Limitation · Known Issue

| 구분 | 내용 |
|---|---|
| Single Replica | Prometheus·Alertmanager·Grafana는 각 1개다. 교육·PoC 범위이며 Production 금융 HA·규제 준수를 주장하지 않는다. 재기동 중 수집·알림·대시보드 공백이 생긴다 |
| PVC·노드 고정 | 세 PVC는 worker03 local PV다. worker03 장애 때 다른 노드로 옮길 수 없다. `kubelet_volume_stats_*`는 파일시스템 전체(`/home`)를 보여 주므로 PVC별 사용량은 `du`·TSDB 지표로 본다 |
| Retention | Prometheus 로컬 보존 15일·16GB 중 먼저 닿는 쪽. 그보다 오래된 데이터는 남지 않는다. P1-MON-02는 이것을 다시 구현하지 않는다 |
| Resource | requests/limits는 9/26~9/29 관측(66.6시간)과 #15 산식 기준이다. 부하 패턴이 바뀌면 다시 산정한다 |
| 이미지 취약점 | Alertmanager(High 1)·Grafana(High 72)·kube-state-metrics(Critical 1·High 44)는 Phase 1 조건부 예외다(만료 2026-10-26 23:59 KST). Phase 2에서 0/0 대체 digest 교체가 필수다 |
| KSM RBAC 로그 | 최소 권한 RBAC라 KSM 로그에 webhook 설정·CSR·StorageClass 조회 forbidden이 나온다. 쓰는 지표는 정상이다. `--resources=` 축소는 Phase 2 후보 |
| Watchdog 5분 | `absent_over_time(…[5m])`는 마지막 샘플 뒤 5분 + 평가 간격(15초) 안에 firing한다(실측 5분 11.0초). "5분 이내" AC 해석은 Lead 결정 기록·QA 수용 대기([#17](https://github.com/321Team/fds-project-baseline/issues/17#issuecomment-5945429945)) |
| receiver 알림 | monitor01 receiver에는 Alertmanager가 없다. Watchdog firing은 외부로 발송되지 않고 receiver API로만 확인한다. IF-24(Alertmanager → monitor01)는 구성하지 않는다 |
| 컨테이너 자동 재시작 없음 | 유닛은 재부팅 지속성만 다룬다. 실행 중 컨테이너가 죽으면 4.1대로 유닛을 재시작한다. 부팅 때 이전 컨테이너 로그는 회수와 함께 사라진다 |
